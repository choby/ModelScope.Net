# ModelScope.Net 迁移计划

## 1. 计划目标

本计划将 ModelScope 的模型仓库与推理能力逐步引入 .NET 平台，交付原生 Hub 客户端、模型能力检测、统一调用接口、Remote/ONNX/GGUF/Python 多运行时，以及可重复的兼容认证和生产运维能力。

计划不迁移 ModelScope 全部 Python 模型实现和训练系统。Python 生态作为受控运行时保留，高价值模型家族通过认证后逐步迁入 ONNX 或 GGUF 本地运行时。

## 2. 实施原则

- 先下载、后调用，先建立稳定的模型获取能力。
- 先契约、后适配，先定义输入输出和错误模型。
- 先兜底、后原生，先用 Python 保证覆盖，再逐个原生化。
- 先模型家族、后模型数量，避免一次性模型代码。
- 每个阶段有独立交付物、验收门槛和停止条件。
- 兼容性声明必须由固定 Revision 和自动化测试支撑。

## 3. 总体节奏

| 阶段 | 建议周期 | 主要结果 |
|---|---:|---|
| 阶段 0：范围与基线 | 2～3 周 | 样本模型、契约、风险和性能基线 |
| 阶段 1：Hub MVP | 6～8 周 | 可用的 .NET 下载 SDK/CLI |
| 阶段 2：运行时骨架 | 6～8 周 | 能力检测、路由、Remote/Python |
| 阶段 3：本地原生推理 | 8～12 周 | 首批 ONNX/GGUF 模型认证 |
| 阶段 4：生产化 | 8～12 周 | 安全、监控、扩缩容和发布 |
| 阶段 5：持续扩展 | 持续 | 新任务与模型家族认证 |

阶段必须按后文并行计划执行。推荐投入为 5.0～6.0 有效 FTE（包含共享 QA/SRE/安全投入）：5.0 FTE 以 8 个月为目标并允许 ONNX/GGUF 串行，6.0 FTE 可提高并行度并以 6～7 个月为目标。技术预览版目标仍为 8～12 周。只有减少 GGUF、GPU 或生产安全范围时，才可采用 4～5 个月的加速版本。

### 技术预览版定义

8～12 周预览版必须包含：

- 阶段 0 已批准的范围、DTO、威胁模型和发布清单草案。
- Hub 对公开测试仓库的查询、固定 Revision 下载、续传、校验和缓存。
- inspect 能力报告。
- 一个 API Inference 固定模型的流式调用。
- 一个固定 Python 模型通过隔离 Worker 调用。
- 端到端日志、基础指标和结构化错误。

预览版不承诺私有/受限仓库生产支持、ONNX/GGUF Certified、GPU SLO、远程不可信代码或商业 SLA。

### 1.0 生产版定义

1.0 必须包含：

- .NET 10 LTS；Windows x64 CPU、Ubuntu x64 CPU，以及发布清单冻结的 Linux NVIDIA GPU 组合。
- Hub 公开、私有和受限仓库支持及生产缓存。
- Remote、ONNX、Python 三种生产运行时。
- 至少一个 GGUF 文本生成模型家族认证。
- Embedding、文本分类、文本生成，以及图像分类/目标检测二选一。
- 固定 5～10 个 Model ID/Commit 的 Certified Catalog。
- 安全隔离、OpenTelemetry、SLO、灰度、回滚和 72 小时稳定性测试。

### 并行关键路径

| 时间 | Hub 流 | Runtime 流 | 模型认证流 | 生产化流 |
|---|---|---|---|---|
| 第 1～3 周 | API 验证 | 契约与路由设计 | 样本及金标准 | 威胁建模 |
| 第 2～8 周 | 下载、缓存、CLI | Worker/Remote 原型 | ONNX/GGUF PoC | CI 与基础遥测 |
| 第 6～12 周 | Hub 加固 | inspect、统一 run | 预览演示模型 | 预览版测试 |
| 第 3～5 月 | 私有/受限及契约测试 | ONNX/GGUF 正式后端 | 5～10 个模型认证 | 安全与容量 |
| 第 5～7 月 | 性能和兼容 | 路由、回退和资源治理 | 持续回归 | SLO、故障演练 |
| 第 7～8 月 | 发布冻结 | 发布冻结 | Catalog 冻结 | 72 小时测试与 1.0 |

关键路径为：阶段 0 决策 → Hub 固定 Revision → 运行时契约/Worker → 首批认证 → 安全与 SLO → 稳定性测试。ONNX/GGUF PoC 可以与 Hub 主开发并行，但正式认证依赖稳定的快照和 Catalog。

## 4. 阶段 0：范围与技术基线

### 目标

把“支持 ModelScope 模型”转化为可测试范围，避免后期因“任意模型”产生无法验收的目标。

### 工作项

1. 选取 15～25 个代表模型：
   - API Inference 文本或多模态模型。
   - ONNX Embedding、分类、图像和检测模型。
   - GGUF 文本生成和 Embedding。
   - 标准 Transformers/Safetensors。
   - Diffusers、音频或语音模型。
   - 需要 trust_remote_code 的模型。
   - 私有或受限测试仓库。
2. 固定 Model ID、Commit、许可证和模型大小。
3. 保存官方 Python 推理输出和性能基线。
4. 定义任务 DTO、流式事件和错误码。
5. 验证元数据、Revision、文件清单、认证和下载接口。
6. 确定首期 OS、CPU/GPU、容器和网络环境。
7. 完成威胁建模和许可证审查流程。

### 交付物

- 模型兼容性基线清单。
- 模型样本和金标准数据集。
- API/DTO 草案。
- 威胁模型。
- 性能与容量基线。
- 1.0 支持范围。

### 退出条件

- release-manifest-v1.yaml 草案列出固定 Model ID、Commit、任务、许可证和硬件矩阵。
- 所有样本模型具有明确候选运行时或明确 Unsupported 原因。
- 下载、检测、加载、调用和认证状态具有可测试定义。
- 首期任务、运行时、SLO 和数值/性能阈值已冻结。
- 技术负责人、产品负责人和安全负责人共同批准；未批准则不得进入 1.0 承诺开发。

## 5. 阶段 1：Hub MVP

### 目标

在不依赖 Python 的情况下，通过 .NET SDK 和 CLI 稳定下载 ModelScope 模型。

### 工作项

1. 创建解决方案与 NuGet 包结构。
2. 实现 Endpoint、Token、Model ID 和 Revision 解析。
3. 实现模型信息、版本和文件列表查询。
4. 实现单文件和快照下载。
5. 实现并发、超时、取消、重试和进度。
6. 实现 HTTP Range 续传和临时文件原子提交。
7. 实现内容 Blob、Snapshot 和 Manifest 缓存。
8. 实现 allow/ignore 规则和离线模式。
9. 实现私有/受限仓库及凭据安全存储。
10. 提供 login、info、download、cache CLI。
11. 建立针对固定测试仓库的每日契约测试。

### 交付物

- ModelScope.Net.Abstractions。
- ModelScope.Net.Hub。
- ModelScope.Net.Cli。
- Hub 单元、集成和契约测试。
- 下载缓存格式说明。

### 验收门槛

- 发布清单中的公开契约仓库全部可下载。
- 私有仓库授权时可下载，未授权时返回正确错误。
- 下载中断后能够续传。
- 损坏文件不会进入有效缓存。
- 多进程下载同一快照不会破坏缓存。
- 日志和异常中不存在 Token。

## 6. 阶段 2：能力检测与运行时骨架

### 目标

为任意已下载仓库返回可解释的能力报告，并打通 Remote API 和 Python Worker。

### 工作项

1. 实现 ModelInspector：
   - 配置、模型卡和文件格式解析。
   - ONNX 元数据和 GGUF Header 检查。
   - 任务、架构、依赖和模型大小推断。
2. 定义 IModelRuntime、IModelSession 和 RuntimeRouter。
3. 实现网络、Python、远程代码、隐私和许可证策略。
4. 实现 Remote API Runtime：
   - Token、流式请求、限流和错误映射。
5. 实现 Python Worker：
   - gRPC 契约和进程生命周期。
   - 模型加载、调用和卸载。
   - 健康检查、重启、依赖和资源诊断。
6. 建立兼容性 Catalog 格式和发布流程。

### 交付物

- ModelScope.Net.Runtime。
- ModelScope.Net.Runtime.Remote。
- ModelScope.Net.Runtime.Python。
- Python Worker 镜像与协议。
- inspect 和 run CLI。

### 验收门槛

- 任意样本仓库返回结构化能力或不支持原因。
- API Inference 样本可通过 .NET 流式调用。
- Python 样本可由 Worker 调用。
- Worker 崩溃不影响网关并能恢复。
- 未授权时不能执行远程模型代码。

## 7. 阶段 3：本地原生推理

### 目标

将高价值、稳定、适合转换的模型家族迁入本地 ONNX/GGUF。

### ONNX 工作项

1. 集成 ONNX Runtime CPU/CUDA。
2. 实现 Session 池、Tensor 生命周期和资源限制。
3. 建立任务适配器框架。
4. 依次实现文本 Embedding、文本分类、图像分类和标准目标检测。
5. 实现相应 Tokenizer、预处理和后处理。
6. 建立与 Python 输出的数值和语义一致性测试。
7. 基准测试吞吐、延迟、内存和显存。

### GGUF 工作项

1. 固定 llama.cpp 版本和分发方式。
2. 通过受控进程或服务管理生命周期。
3. 解析架构、量化、Tokenizer 和 Chat Template。
4. 建立支持架构和量化白名单。
5. 实现文本生成、流式输出和 Embedding。
6. 验证加载错误、OOM 和进程恢复。

### 交付物

- ModelScope.Net.Runtime.Onnx。
- ModelScope.Net.Runtime.Gguf。
- 首批任务适配器。
- 认证 Catalog。
- 性能报告和容量建议。

### 验收门槛

- release-manifest-v1.yaml 中列出的 5～10 个固定 Revision 模型通过认证。
- 至少覆盖 Embedding、分类和文本生成。
- 数值误差满足预设阈值。
- 性能不低于阶段 0 的最低门槛。
- 不兼容模型可降级到 Python 或返回明确诊断。

## 8. 阶段 4：生产化

### 目标

将 SDK 和运行时提升为可部署、可运维、可升级和可审计的产品。

### 工作项

1. ASP.NET Core 依赖注入、健康检查、OpenTelemetry、鉴权限流和配额。
2. 模型预热、LRU 卸载、并发、批处理和 CPU/GPU 资源调度。
3. Worker 沙箱、镜像签名、依赖扫描和远程代码审计。
4. 熔断、重试、降级、回滚及故障演练。
5. NuGet、多架构镜像、示例和运维手册。
6. 建立 ModelScope、ONNX Runtime 和 llama.cpp 升级流程。

### 交付物

- ModelScope.Net.AspNetCore。
- 生产容器镜像。
- Dashboard 和告警。
- 安全评审报告。
- 部署、升级和故障手册。
- 1.0 NuGet 包。

### 验收门槛

- 通过至少 72 小时稳定性测试。
- 下载和推理关键指标达到 SLO。
- 模型及运行时升级可灰度、可回滚。
- Worker 或原生运行时故障不会拖垮网关。
- 安全评审无阻断问题。

## 9. 阶段 5：持续扩展

按业务价值扩展：

1. 增加文本生成 ONNX、ASR、OCR、图像生成等适配器。
2. 将高调用量 Python 模型逐步原生化。
3. 增加 GGUF 架构和硬件后端。
4. 建设社区运行时插件及认证提交流程。
5. 监控上游模型 Revision 和依赖变化。
6. 对认证 Catalog 持续回归和必要时撤销。

## 10. 团队配置

首个生产版本建议 5.0～6.0 有效 FTE，以下共享投入计入总 FTE：

| 角色 | 建议投入 | 职责 |
|---|---:|---|
| 技术负责人/.NET 架构 | 1 | API、架构、质量门槛和关键决策 |
| .NET Hub/基础设施 | 1～2 | 下载、缓存、CLI、鉴权和可靠性 |
| ML Runtime | 1～2 | ONNX、GGUF、Tokenizer 和性能 |
| Python/ML | 1 | Worker、ModelScope 和金标准 |
| QA/SRE/安全 | 共享角色，合计至少 0.5 FTE | 自动化、性能、部署和安全 |

5.0 FTE 配置可按负责人 1、Hub 1、Runtime 1.5、Python/ML 1、QA/SRE/安全共享 0.5 组成，GGUF 与 ONNX 串行推进，生产版目标为 8 个月。6.0 FTE 配置增加 1 FTE Hub 或 Runtime 能力，支持并行计划，目标为 6～7 个月。产品、法务和最终安全批准属于项目治理投入，不计入工程 FTE。如果同时覆盖 CV、NLP、音频和生成式模型，需要增加领域工程师并调整周期。

## 12. 测试迁移策略

不逐文件照搬 Python 测试，而按可观察契约重建：

1. Hub 使用小型、可控、固定 Revision 的测试仓库。
2. 模型测试保存输入、Python 原始输出和容差。
3. 非确定性模型固定 Seed，并检查结构和统计性质。
4. 每个运行时测试加载、推理、卸载和故障恢复。
5. 支持矩阵条目必须关联自动化测试 ID。
6. 只有关联测试全部通过才能标记 Certified。
7. Revision、运行时或适配器变化自动触发重新认证。

## 13. 发布与回滚

### 发布

- SDK、运行时插件和兼容 Catalog 独立版本。
- 预发布通道先验证上游 API 和运行时升级。
- 新模型先进入 Experimental，达到门槛后进入 Certified。
- 生产默认只使用 Certified。

### 回滚

- 固定模型 Revision 和运行时版本。
- 保留上一个 Catalog 和 Worker 镜像。
- 按模型切回 Python 或 Remote 后端。
- 缓存 Manifest 并存，回滚不覆盖有效 Blob。
- 数值、性能或安全回归时自动撤销认证。

## 14. 关键指标

### Hub

- 发布清单契约套件连续 7 天、至少 2,000 次尝试成功率不低于 99.5%。
- 缓存命中率和重复下载字节数。
- 中断恢复成功率。
- 文件完整性错误检出率。

### Runtime

- 发布清单中所有模型都必须返回正确的候选运行时或 Unsupported 原因；统一返回 Unsupported 不算检测正确。
- 认证模型在 72 小时稳定性测试中的加载成功率不低于 99.9%。
- 推理成功率、P95 延迟和吞吐。
- Python 降级比例和原因。
- Worker 崩溃和 OOM 数量。

### 产品

- 正式认证的模型家族和任务数量。
- 新模型完成认证的平均时间。
- 升级引入的兼容回归数量。
- 无诊断信息的不支持错误应为 0。

## 15. 决策检查点

### 检查点 A：阶段 0 结束

确认模型、任务、平台和运行时范围。如果目标变成“纯 .NET 任意模型”，暂停并重新评估。

### 检查点 B：Hub MVP 结束

确认官方接口稳定性、缓存方案和维护成本。必要时将 modelscope-hub Sidecar 作为临时兼容层。

### 检查点 C：首批原生模型完成

比较 ONNX/GGUF 与 Python 的性能、兼容性和维护成本，决定后续原生化优先级。

### 检查点 D：生产发布前

确认安全隔离、许可证流程、SLO、容量和故障恢复通过评审。

## 16. 实施前待确认

1. 首期必须支持的 Model ID、任务和 Revision。
2. 是否允许部署 Python Worker。
3. 是否允许独立 llama.cpp 原生进程。
4. 是否允许访问 ModelScope API Inference。
5. 目标 OS、CPU、GPU、CUDA 和部署环境。
6. 离线、内网、数据隐私和商业 SLA 要求。
7. 私有/受限模型及许可证审核责任。
8. 1.0 对模型覆盖范围的正式承诺方式。

责任与时限：

| 决策 | 负责人 | 截止 |
|---|---|---|
| 模型、任务、覆盖承诺、SLA | 产品负责人 | 阶段 0 第 2 周 |
| Python、llama.cpp、API Inference 策略 | 技术负责人 | 阶段 0 第 2 周 |
| OS、CPU/GPU、CUDA 和部署矩阵 | 技术负责人/SRE | 阶段 0 第 2 周 |
| 隐私、许可证、受限模型和远程代码 | 安全/法务负责人 | 阶段 0 第 3 周 |
| release-manifest-v1.yaml 最终批准 | 产品、技术、安全共同负责 | 阶段 0 结束 |

这些事项未确认前可以推进 Hub 研究、抽象和技术验证，但不得进入 1.0 正式排期或承诺具体模型覆盖率。

## 17. 发布 Go/No-Go

技术预览版由技术负责人批准，条件为预览版定义中的必选演示全部通过，且不存在高危 Token 泄漏或任意代码执行问题。

1.0 由产品、技术和安全负责人共同批准，条件为：

- release-manifest-v1.yaml 中所有必选条目通过。
- Hub、Runtime、SLO、数值、性能和安全门槛均有测试证据。
- 72 小时稳定性测试通过。
- 灰度和回滚演练通过。
- 不存在阻断级安全或许可证问题。

任一必选运行时无法达到门槛时，应缩减并重新批准发布范围，而不是用 Experimental 状态替代 Certified。
